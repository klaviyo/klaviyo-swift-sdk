# Klaviyo Client API — what a mobile SDK can use to cut requests and bytes

Researched 2026-09-30 against primary sources only: developers.klaviyo.com reference pages, the API changelog,
the rate-limits doc, and Klaviyo's published OpenAPI spec (`openapi/stable.json`, `info.version: 2026-07-15`,
https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable/…). Quotes are verbatim. Anything the
docs do not state is marked **UNVERIFIED**.

Default `revision` header on every Client endpoint below: `2026-07-15` (format `YYYY-MM-DD[.suffix]`).
Every Client endpoint below returns `202` on success, `4XX` client error, `5XX` server error — no other
documented codes.

---

## 1. `POST /client/event-bulk-create` (Bulk Create Client Events)

Source: https://developers.klaviyo.com/en/reference/bulk_create_client_events
OpenAPI: https://raw.githubusercontent.com/klaviyo/openapi/main/openapi/stable/apis/bulk_create_client_events.json

**Description (verbatim):**
> "Create new events to track a profile's activity.
> This endpoint is specifically designed to be called from publicly-browseable, client-side environments only
> and requires a public API key (site ID). Never use a private API key with our client-side endpoints.
> Do not use this endpoint from server-side applications. To create events from server-side applications,
> instead use POST /api/event-bulk-create-jobs.
> Accepts a maximum of `1000` events per request.
> *Rate limits*: Burst: `10/s` Steady: `150/m`"

Scope: `events:write`. Header: `company_id` (public API key / site ID), `revision`.

### Payload schema (from OpenAPI, `*` = required)

```
data*                     object
  type*                   "event-bulk-create"
  attributes*             object
    backfill              boolean   "When true, the event is recorded but does NOT trigger flows. ..."
    profile*              object
      data*               object
        type*             "profile"
        id                string    "Primary key that uniquely identifies this profile. Generated by Klaviyo."
        attributes*       object
          email, phone_number, external_id, anonymous_id, _kx,
          first_name, last_name, organization, locale, title, image,
          location          object {address1, address2, city, country, latitude, longitude, region, zip, timezone, ip}
          properties        object "An object containing key/value pairs for any custom properties assigned to this profile"
        meta                object
          patch_properties  {append, unappend, unset}
          patch_identifiers {append, unappend}
    events*               object
      data*               array (no maxItems in schema; 1000 cap is in prose)
        [i]
          type*           "event"
          attributes*     object
            metric*       { data*: { type*: "metric", attributes*: { name* (string, "<128 chars"), service } } }
            properties*   object
            time          string (ISO 8601)
            value         number
            value_currency string (ISO 4217)
            unique_id     string
            backfill      boolean
```

Per-event fields — all present (`properties` required; `time`, `value`, `value_currency`, `unique_id` optional):
- `properties`: "Properties of this event (must not exceed 400 properties). The size of the event payload must not
  exceed 5 MB, and each string cannot be larger than 100 KB."
- `time`: "When this event occurred. By default, the time the request was received will be used. The time is
  truncated to the second. The time must be after the year 1990 and can only be up to 1 year in the future."
- `value`: "A numeric, monetary value to associate with this event. For example, the dollar amount of a purchase."
- `value_currency`: "The ISO 4217 currency code of the value associated with the event."
- `unique_id`: "A unique identifier for an event. If a unique_id is repeated for the same profile and metric, the
  request will fail and no events will be processed. If this field is not present, this field will use the time to
  the second. Using the default, this limits only one event per profile per second."
  -> **SDK consequence:** two events with the same metric in the same second and no `unique_id` will fail the
  whole request ("no events will be processed"). An SDK batching by this endpoint must set `unique_id` per event.

Profile block accepts: `anonymous_id` YES (no description in schema), `_kx` YES ("Also known as the `exchange_id`,
this is an encrypted identifier used for identifying a profile by Klaviyo's web tracking."), profile `properties`
YES, `location` YES, `meta.patch_properties` YES. **`push_token`: NO** — does not appear anywhere in the profile
block.

### One profile per request?
**YES, structurally.** The schema has exactly one `data.attributes.profile` object and an `events.data[]` array
beneath it; there is no per-event profile field. The reference page does *not* state this in a sentence — the
profile/events objects carry no description text — so there is no verbatim "one profile" quote to cite
(**UNVERIFIED as prose; VERIFIED by schema**). Contrast with the server-side endpoint, which the Events API overview
(https://developers.klaviyo.com/en/reference/events_api_overview) describes as "creating multiple events for one
or more profiles at a time" — that is `/api/event-bulk-create-jobs`, private key, not usable from an SDK.
-> **SDK consequence:** events for different profiles (e.g. before/after `setEmail` identity change) must go in
separate bulk requests; batches must be keyed by the profile identity snapshot.

### Limits
- Max events per request: "Accepts a maximum of `1000` events per request."
- Size: "The size of the event payload must not exceed 5 MB, and each string cannot be larger than 100 KB."
  Rate-limits doc: "We enforce a maximum total payload size of 5 MB (decompressed) for all of our new APIs."
  Events API overview Limitations table: Max payload size 5 MB decompressed; max event properties per event 400;
  max string 100 KB; max array items 4000; max nesting 11; timestamp 1990.."now"+1 year; `unique_id` 1-255 chars;
  max event profile object 95 KB. (Note: the rate-limits doc's own list says 300 properties / nesting 10 — the
  two pages disagree; treat 300/10 as the safe bound.)
- Rate limits: **Burst `10/s`, Steady `150/m`** (vs 350/s, 3500/m for single `/client/events`). The bulk endpoint
  is rate-limited per *request*, so 150 requests/min x 1000 events = up to 150k events/min per site vs 3500/min
  single-event. But a chatty SDK that flushes >10 times/s per site (across all devices — limits are per account,
  see §5) would 429 far sooner than with `/client/events`. **UNVERIFIED** whether Client limits are per-site or
  per-device/IP; the docs say nothing.

### Error behaviour
- Responses documented: `202` Success, `4XX`, `5XX` — no body examples on the reference page.
- Error object schema (OpenAPI `ErrorSource`): `pointer` — "A pointer to the source of the error in the request
  payload." example/default `"/data"`. So a validation error *can* point into the body, and JSON-pointer syntax
  would be e.g. `/data/attributes/events/data/3/attributes/metric` — **UNVERIFIED**: no doc shows an index-level
  pointer for the bulk endpoint.
- Whole batch rejected on one bad event? Only stated for duplicate `unique_id`: "the request will fail and no
  events will be processed." For other per-event validation failures: **UNVERIFIED** (rate-limits doc: "No
  discussion of batch/bulk requests being wholly or partially rejected"). Design assumption: all-or-nothing.

### Revision support
Changelog (https://developers.klaviyo.com/en/docs/changelog_), revision **`2023-07-15` (GA)**:
> "Bulk Create Client Events: It is now easier and more performant to track activity for a profile from
> client-side contexts, such as the browser."
Present in every revision since; current default `2026-07-15`. Note the changelog framing ("for a profile") is
consistent with the one-profile schema.

## 2. `POST /client/events` (Create Client Event) — comparison

Source: https://developers.klaviyo.com/en/reference/create_client_event
- Rate limits: **Burst `350/s`, Steady `3500/m`** (35x the bulk endpoint's request rate).
- `data.type: "event"`; `attributes`: `metric*` (same nested metric object), `profile*` (same profile upsert object
  incl. `anonymous_id`, `_kx`, `properties`, `location`, `meta.patch_*`), `properties*`, `time`, `value`,
  `value_currency`, `unique_id`.
- Extra note (verbatim): "Note that to update a profile's existing identifiers (e.g., email), you must use a
  server-side endpoint authenticated by a private API key. Attempts to do so via client-side endpoints will return
  a 202, however the identifier field(s) will not be updated."
- Bytes: one event per request repeats the full profile block each time; bulk sends it once.

## 3. Other Client write endpoints

| Endpoint | data.type | Burst | Steady | Source |
|---|---|---|---|---|
| `POST /client/profiles` | `profile` | `350/s` | `3500/m` | https://developers.klaviyo.com/en/reference/create_client_profile |
| `POST /client/push-tokens` | `push-token` | `150/s` | `1400/m` | https://developers.klaviyo.com/en/reference/create_client_push_token |
| `POST /client/push-token-unregister` | `push-token-unregister` | `10/s` | `150/m` | https://developers.klaviyo.com/en/reference/unregister_client_push_token |
| `POST /client/subscriptions` | `subscription` | `350/s` | `750/m` | https://developers.klaviyo.com/en/reference/create_client_subscription |
| `POST /client/back-in-stock-subscriptions` | `back-in-stock-subscription` | `350/s` | `3500/m` | https://developers.klaviyo.com/en/reference/create_client_back_in_stock_subscription |

**`/client/profiles`** attributes: `email, phone_number, external_id, anonymous_id, _kx, first_name, last_name,
organization, locale, title, image, location, properties`; `meta.patch_properties {append, unappend, unset}`,
`meta.patch_identifiers {append, unappend}`. Same identifier caveat as §2 (202 but identifiers not updated).

**`/client/push-tokens`** attributes (all required per page): `token`, `platform` (`android|ios`),
`enablement_status` (`AUTHORIZED|DENIED|NOT_DETERMINED|PROVISIONAL|UNAUTHORIZED`, default AUTHORIZED), `vendor`
(`apns|fcm`), `background` (`AVAILABLE|DENIED|RESTRICTED`, default AVAILABLE), `device_metadata` (`device_id,
klaviyo_sdk, sdk_version, device_model, os_name, os_version, manufacturer, app_name, app_version, app_build,
app_id, environment`), `profile*`.
**Does push-tokens accept profile properties? YES.** Profile attribute keys in the OpenAPI schema:
`phone_number, external_id, _kx, first_name, last_name, organization, locale, title, image, location, properties,
email`, plus `meta.patch_properties` / `meta.patch_identifiers`. **`anonymous_id` is NOT in the push-token profile
schema** (it is in `/client/profiles` and `/client/events`). So a profile-attribute update + token registration
can be a single `/client/push-tokens` call — but only if the profile is identified by email/phone/external_id/_kx,
not solely by `anonymous_id`. **UNVERIFIED** whether the server rejects or ignores an `anonymous_id` key here.
Description: "This endpoint is specifically designed to be called from our mobile SDKs (iOS and Android) ... You
must have push notifications enabled to use this endpoint."

**`/client/push-token-unregister`**: `token*`, `platform*`, `vendor`, `profile*` (same upsert object). Note the low
limit (10/s, 150/m) — same tier as bulk events.

**`/client/subscriptions`**: `attributes.custom_source`, `attributes.profile*` (with `subscriptions` object);
`relationships.list*`. "One of either `email` or `phone_number` must be provided." Changelog `2023-02-22`: "The
steady rate limit for Create Client Subscription has increased to 700/m" (page now says 750/m).

Full list of `/client/*` paths in the stable OpenAPI spec: `review-values-reports, reviews, geofences,
subscriptions, push-tokens, push-token-unregister, events, profiles, event-bulk-create,
back-in-stock-subscriptions, ip-allowlists/{id}`. No other bulk/batch Client endpoint exists (no bulk profiles,
no bulk push-tokens).

## 4. Compressed request bodies (`Content-Encoding: gzip`)

**UNVERIFIED — docs are silent.**
- API overview (https://developers.klaviyo.com/en/reference/api_overview): request compression / Content-Encoding /
  gzip / Accept-Encoding — NOT MENTIONED; request size limits — NOT MENTIONED.
- Rate limits & error handling doc: no "gzip", "Content-Encoding", or "compress" anywhere.
- Stable OpenAPI spec: zero occurrences of `gzip`, `content-encoding`, `compress`.
- Changelog: "No entries about gzip compression or request size limits."
- The only hint is the phrase "maximum total payload size of 5 MB (**decompressed**)" (rate-limits doc) and
  "5 MB decompressed" (Events API overview Limitations), which implies the ingest path *can* receive compressed
  bodies — but nothing documents that clients may send `Content-Encoding: gzip`, which encodings are accepted, or
  Client-endpoint behaviour. Must be verified empirically against `a.klaviyo.com` before relying on it.

## 5. Rate-limit headers and 429 / `Retry-After`

Source: https://developers.klaviyo.com/en/docs/rate_limits_and_error_handling
- Algorithm: "a fixed-window rate limiting algorithm with two distinct windows: burst (1-second window) and steady
  (1-minute window)."
- Headers on normal responses:
  - `RateLimit-Limit`: "The number of requests allowed per time period"
  - `RateLimit-Remaining`: "The approximate number of requests remaining within a window"
  - `RateLimit-Reset`: "Number of seconds remaining before current window resets"
- On 429: "those headers are replaced with a `Retry-After` header that returns an `int` indicating the number of
  seconds before you can start making requests."
- Retry guidance: "A retry should only be attempted after the current rate limit is lifted, i.e., the time (in
  seconds) indicated by the `Retry-After` header on a 429 response has expired."
- Error body example (verbatim):
  ```json
  {"errors":[{"id":"2c76424d-b1ff-4afd-a2a1-728d85dac775","status":400,"code":"invalid","title":"Invalid input.",
    "detail":"'profiless' is not an allowed include parameter for this resource.",
    "source":{"parameter":"include"},"meta":{}}]}
  ```
  `source.parameter` for query params; `source.pointer` (OpenAPI `ErrorSource`) for body: "A pointer to the source
  of the error in the request payload."
- Whether `/client/*` endpoints emit these headers, and whether Client limits are per site vs per device/IP:
  **UNVERIFIED** — "No Client API-specific text about rate-limit headers or 429 responses."

## 6. Client endpoint for in-app forms / onsite configuration

**None documented.**
- The stable OpenAPI spec has no `/onsite/*` paths and no GET under `/client/*` (all Client endpoints are POST
  create-only, except `/client/ip-allowlists/{id}`). API overview: "Client endpoints are specifically designed to
  limit functionality to object creation of specific types of objects and do not respond with any potentially
  sensitive response data."
- Forms API exists only as **private-key** endpoints: `GET /api/forms`, `GET /api/forms/{id}` ("Get the form with
  the given ID.", scope `forms:read`, Klaviyo-API-Key auth, 3/s burst, 60/m steady), `GET /api/form-versions/{id}`,
  `GET /api/forms/{id}/form-versions`, `POST /api/forms`, plus form reports. Changelog: `2024-07-15` "Get forms and
  related form versions via our Forms API."; `2025-07-15.pre`/`2025-10-15` "Retrieve a form and its definition
  with the Forms API." / "Use the Create Form endpoint to generate a new form". Not callable with a public key
  (private key must never ship in an app), so not usable by the SDK.
- SDK overview (https://developers.klaviyo.com/en/docs/sdk_overview) mentions "In-app forms — surface pop-up
  experiences without leaving the app" but the delivery mechanism is NOT MENTIONED. Dedicated in-app-forms doc
  pages tried (`/docs/in-app_forms_in_mobile_sdks`, `/docs/get_started_with_klaviyo_in-app_forms`,
  `/docs/introduction_to_the_klaviyo_swift_sdk`) returned 404.
- Non-doc context (this repo, not a public API contract): `Sources/KlaviyoForms/InAppForms/IAFWebViewModel.swift`
  loads `https://static.klaviyo.com/onsite/js/klaviyo.js?company_id=<key>&env=in-app` into a WKWebView and the
  JS fetches form config itself; `Sources/KlaviyoCore/Networking/KlaviyoEndpoint.swift` also posts to
  `/onsite/track-analytics` and `/client/geofences`. Neither `/onsite/*` route is on developers.klaviyo.com —
  **UNVERIFIED / undocumented**.

## Summary of SDK-relevant levers (all from the above)

1. `POST /client/event-bulk-create` is the only documented request-count reducer: up to 1000 events, one profile
   block per request, 5 MB body, 202 on success, all-or-nothing on duplicate `unique_id` — but only 10/s / 150/m
   vs 350/s / 3500/m for singles, so it trades per-request headroom for fewer requests. Set `unique_id` per event.
2. `/client/push-tokens` carries a full profile upsert (properties, location, patch_properties) — token + profile
   update can be one call, except it lacks `anonymous_id`.
3. No documented bulk profile, bulk push-token, or mixed-type batch endpoint; no documented gzip request support;
   no public forms-config endpoint.
